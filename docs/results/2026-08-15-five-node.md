# Five-node Raft benchmark and failover results

Date: 2026-08-15

Implementation commit: `78322d0`

These measurements characterize the educational Raft implementation and its
full-log JSON persistence. They are not claims about production database
throughput, WAN behavior, or optimized storage engines.

## Environment

- Apple M1 Pro, 10 CPU cores, 16 GB memory
- macOS 26.5.2
- Go 1.26.5 (`darwin/arm64`); module language/toolchain floor Go 1.25
- Docker Engine 29.2.1
- five node containers, one persistent volume per node
- election timeout 350-700 ms, heartbeat 100 ms, peer RPC timeout 250 ms
- benchmark traffic sent to a follower to exercise one-hop forwarding

## Steady mixed workload

Configuration: 32 clients, 15 seconds, 64 keys, 64-byte values, 50% `PUT` and
50% linearizable `GET`. Mixed keys were seeded outside the timed window. Every
GET commits a Raft barrier and therefore exercises the replicated persistence
path rather than serving a local cache read.

## Leader failure without sustained load

The packaged failover demo committed a value, stopped the detected leader,
waited for a different leader, committed another value, restarted the failed
node, and waited for its commit index to catch up.

| Replacement election | Post-failover write | Restarted-node catch-up |
| ---: | --- | --- |
| 763 ms | Succeeded | Commit index reached 4,276 before verification read |

The exact commit index includes the preceding steady benchmark and is not a
performance metric. Its purpose is to show that the restarted follower caught
up to the replacement leader before the final value was checked.

## Leader failure during write load

A fresh isolated cluster received a 32-client write workload for 15 seconds.
Traffic targeted a follower that remained alive. The script stopped the current
leader five seconds into the run and restarted it afterward.

| Replacement | Successful operations | Errors | Error rate | Success throughput | p95 successful latency |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 2.144 s | 2,858 | 1,395 | 32.80% | 190.50 ops/s | 165.89 ms |

Error breakdown: 1,363 HTTP 503 responses and 32 transport failures. The 503s
are the explicit no-leader/election response. Transport failures came from
requests already being forwarded to the leader when its container stopped;
their commit outcome can be unknown.


After the stopped node restarted, Prometheus reported:

- exactly one active leader;
- zero difference between maximum and minimum commit index; and
- all five node scrape targets healthy before shutdown.

## Interpretation

The experiments demonstrate majority safety, replacement election, post-failure
commits, and follower catch-up. They do not demonstrate zero-downtime failover.
Clients see an availability gap during election and need bounded, deadline-aware
retry behavior.

The loaded election was slower than the configured 350-700 ms timeout. The most
plausible contributing factor is the intentionally expensive persistence path:
every term, vote, append, commit, and read barrier rewrites and `fsync`s the
complete growing JSON log. This is an inference from the architecture and result,
not a separately isolated causal benchmark.

## Reproduce

```bash
COMPOSE_PROJECT_NAME=raft-kv-benchmark JSON_OUTPUT=1 \
  CONCURRENCY=32 DURATION=15s WORKLOAD=mixed KEYSPACE=64 VALUE_BYTES=64 \
  ./scripts/benchmark.sh

COMPOSE_PROJECT_NAME=raft-kv-failover \
  CONCURRENCY=32 DURATION=15s KEYSPACE=64 VALUE_BYTES=64 FAIL_AFTER_SECONDS=5 \
  ./scripts/failover-load.sh
```

Use a fresh Compose project name for controlled runs so old log growth does not
bias a new measurement. Remove only disposable experiment volumes when finished.
